# The ApiPilot software supply-chain contract

This document describes the artifacts ApiPilot produces to make its
supply chain verifiable: a software bill of materials, signed NuGet
packages, and build provenance. It is a working contract, not a marketing
claim. Where this document and the pipeline disagree, the pipeline wins
and this document is corrected.

## What this document covers

- The SBOM: what it contains and how it is produced.
- Package signing: the CI-only, fail-closed rule.
- Build provenance: what the artifact records.
- The release pipeline as a whole.
- What the pipeline does not prove.

## The SBOM

ApiPilot produces an SPDX 2.3 JSON software bill of materials. The
document is generated by a repository-owned PowerShell script,
scripts/generate-sbom.ps1. No third-party SBOM library is used.

The SBOM lists the three production packages: ApiPilot.Core,
ApiPilot.AspNetCore, and ApiPilot.Security. Each entry carries the
package name, the repository version read from the VERSION file, the
declared license (MIT), and NOASSERTION where the repository has no
authoritative value. The document is honest about what it knows.

ApiPilot has no third-party runtime dependencies. The zero-dependency
policy is enforced by audit.ps1. The SBOM therefore lists no third-party
components, and that absence is the point: the document reflects the
repository as it is.

To generate the SBOM:

    powershell -NoProfile -ExecutionPolicy Bypass -File scripts/generate-sbom.ps1

The output is written to artifacts/sbom/apipilot-<version>.spdx.json.

## Package signing

NuGet packages are signed in the release workflow, .github/workflows/release.yml.
Signing uses dotnet nuget sign with a certificate supplied by CI. The
signing step is fail-closed: if the signing certificate secret is not
configured, the workflow refuses to publish. It never publishes unsigned
packages silently.

The local build signs nothing. A signature without a real certificate
would be a lie. The certificate is a CI-supplied secret; the local
developer cannot and does not fabricate one.

## Build provenance

The release workflow records a provenance artifact at
artifacts/provenance/provenance.json. It carries the repository version,
the commit SHA, the workflow run id, the run URL, the repository name, and
the build timestamp. The provenance is plain JSON produced from the
workflow environment. It introduces no runtime dependency.

## The release pipeline

The release pipeline runs on a tag push matching v* or on manual
dispatch. It has two jobs.

The build-and-test job runs on ubuntu-latest. It restores, builds the
solution, and runs the five .NET test harnesses. A failure in any harness
stops the release.

The sign-and-package job runs on windows-latest and depends on the
build-and-test job. It requires the signing certificate, packs the
packages, signs them, generates the SBOM, records provenance, and uploads
the artifacts: the signed packages, the SBOM, and the provenance JSON.

The pipeline uses only the official GitHub actions: actions/checkout,
actions/setup-dotnet, and actions/upload-artifact. No third-party action
is referenced.

## What the pipeline does not prove

This section is deliberate. It names the limits of the evidence.

- The SBOM lists what the repository declares. It is not an independent
  analysis of the compiled binary.
- The provenance records the build inputs. It is not a cryptographic
  attestation signed by a hardware root of trust.
- The pipeline does not claim regulatory compliance. Compliance is a
  property of a deployment and its operator, not of a build artifact.
- The absence of third-party components is asserted by the audit over the
  source tree and the compiled assembly references. It is not a byte-level
  scan of a running process.

An artifact is evidence of what was built. It is not proof of security.
ApiPilot reports what it produces and what it does not.
